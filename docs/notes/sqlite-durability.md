# SQLite durability for a single-writer local workflow store

Researched: 2026-09-16. Scope: sqlite.org documentation pages (`wal.html`, `pragma.html`, `rescode.html`, `lang_transaction.html`, `c3ref/busy_handler.html`, `c3ref/busy_timeout.html`, `howtocorrupt.html`, `useovernet.html`) fetched and text-extracted on that date; rusqlite 0.40.2 (2026-08-08), rusqlite_migration 2.6.0, tokio-rusqlite 0.8.0 (2026-09-06), sqlx 0.9.0 (2026-05-21) docs and source. Lighter template: "Execution model", "Step and operation identity", "Fan-out", "Versioning", "Schedules", "Cancellation" do not apply and are omitted; the remaining sections are reshaped around the questions asked (WAL, synchronous, busy handling, network FS, checkpointing, pragmas, rusqlite vs sqlx).

## Summary
SQLite in WAL mode gives one writer plus concurrent readers on one host, durability that depends on `PRAGMA synchronous` (FULL = durable across power loss; NORMAL = durable across application crashes only), and a busy-handler model that does not help a deferred transaction upgrading to a write. All of this is documented precisely, so a single-owner workflow store can set a small fixed set of pragmas and use `BEGIN IMMEDIATE` for every write. For Rust, `rusqlite` (sync, `Connection: Send + !Sync`) on a dedicated writer thread is the simplest fit for Flowyard's serialized write path; `sqlx` adds async and compile-time-checked queries but runs each connection on its own OS thread anyway and needs care with pools and deferred transactions.

## Deployment and process model (what SQLite assumes)
- One host: "All processes using a database must be on the same host computer; WAL does not work over a network filesystem. This is because WAL requires all processes to share a small amount of memory and processes on separate host machines obviously cannot share memory with each other." (wal.html §Overview). Also: "the use of shared memory means that all readers must exist on the same machine. This is why the write-ahead log implementation will not work on a network filesystem." (wal.html §3)
- Network filesystems generally (useovernet.html): the "remote database" approach "is usually not the best way to use a single SQLite database from multiple systems, (even if it appears to "work"), as it often leads to various kinds of trouble and grief. Because these problems are inevitable with some usages, but not frequent or repeatable, it behooves application developers to not rely on early testing success". howtocorrupt.html §2.1: "some filesystems contain bugs in their locking logic such that the locks do not always behave as advertised. This is especially true of network filesystems and NFS in particular."
- One writer: "since there is only one WAL file, there can only be one writer at a time." (wal.html §3). Readers and the writer proceed concurrently; "A checkpoint can run concurrently with readers".
- Files: "There is an additional quasi-persistent "-wal" file and "-shm" shared memory file associated with each database." "It is not possible to open read-only WAL databases" without write access to `-shm` or the directory (wal.html §Overview; relaxed in 3.22 with `immutable`).
- Single-process alternative: "WAL databases can be created, read, and written even if shared memory is unavailable as long as the locking_mode is set to EXCLUSIVE before the first attempted access. In other words, a process can interact with a WAL database without using shared memory if that process is guaranteed to be the only process accessing the database." (wal.html §Implementation of Shared-Memory). In EXCLUSIVE mode "the database connection never releases file-locks" (pragma.html); this is an OS-lock-backed single-owner guarantee at the SQLite layer, at the cost of blocking any other connection (including inspection tools) while the owner is open.

## Persistence schema (how WAL and checkpoints behave)
- WAL basics (wal.html §2): changes are appended to the WAL; a COMMIT is a commit record appended to the WAL; readers use the wal-index in shared memory (`-shm`) to find pages; "Moving the WAL file transactions back into the database is called a 'checkpoint'."
- Automatic checkpoint (wal.html §3.1, verbatim): "By default, SQLite will automatically checkpoint whenever a COMMIT occurs that causes the WAL file to be 1000 pages or more in size, or when the last database connection on a database file closes." `PRAGMA wal_autocheckpoint` (default 1000; 0 disables). "By default, the checkpoint will be run automatically by the same thread that does the COMMIT that pushes the WAL over its size limit. This has the effect of causing most COMMIT operations to be very fast but an occasional COMMIT (those that trigger a checkpoint) to be much slower."
- Checkpoints need readers to finish (wal.html §2.2/§Avoiding Excessively Large WAL Files): "the checkpoint must stop when it reaches a page in the WAL that is past the end mark of any current reader"; "Checkpoint starvation. A checkpoint is only able to run to completion, and reset the WAL file, if there are no other database connections using the WAL file. If another connection has a read transaction open, then the checkpoint cannot reset the WAL file because doing so might delete content out from under the reader."
- Checkpoint modes (pragma.html `wal_checkpoint`): PASSIVE — "Checkpoint as many frames as possible without waiting for any database readers or writers to finish. ... The busy-handler callback is never invoked in this mode."; FULL — "blocks (invokes the busy-handler callback) until there is no database writer and all readers are reading from the most recent database snapshot. It then checkpoints all frames in the log file and syncs the database file. FULL blocks concurrent writers while it is running, but readers can proceed."; RESTART — as FULL plus "blocks ... until all readers are finished with the log file. This ensures that the next client to write to the database file restarts the log file from the beginning."; TRUNCATE — as RESTART plus "the WAL file is truncated to zero bytes upon successful completion." Returns `(busy, log, checkpointed)`.
- Checkpoint syncs (wal.html §2.3): "Checkpointing does require sync operations in order to avoid the possibility of database corruption following a power loss or hard reboot. The WAL must be synced to persistent storage prior to moving content from the WAL into the database and the database file must be synced prior to resetting the WAL."
- WAL mode is persistent: "The WAL journaling mode is persistent; after being set it stays in effect across multiple database connections and after closing and reopening the database." "the journal_mode cannot be changed while a transaction is active." Page size cannot be changed in WAL mode.
- Journal size: `PRAGMA journal_size_limit` caps the WAL file left behind after checkpoints.

## Crash recovery of in-flight work (durability semantics of `synchronous`)
Condensed from the verbatim text below (WAL mode column is what matters for Flowyard):

| `synchronous` | App crash | OS crash / power loss (WAL) | Syncs per commit (WAL) |
|---|---|---|---|
| OFF | safe | "might become corrupted" | none |
| NORMAL | durable | consistent, "might roll back" (last transactions lost) | none; checkpoint syncs only |
| FULL | durable | "atomic, consistent, isolated, and durable (ACID) in WAL mode" | WAL synced every commit |
| EXTRA | durable | same as FULL ("no different from FULL in WAL mode") | as FULL |

pragma.html `PRAGMA synchronous`, verbatim:
- FULL (2): "When synchronous is FULL (2), the SQLite database engine will use the xSync method of the VFS to ensure that all content is safely written to the disk surface prior to continuing. This ensures that an operating system crash or power failure will not corrupt the database. FULL is the default synchronous mode for a rollback journal. FULL is atomic, consistent, isolated, and durable (ACID) in WAL mode and is atomic, consistent, and isolated with a rollback journal. FULL might also be durable using a rollback journal, depending on the underlying filesystem. FULL is not necessarily durable across a power loss in rollback mode, so if durability is desired, it is best to set the synchronous mode to EXTRA."
- NORMAL (1): "When synchronous is NORMAL (1), the SQLite database engine will still sync at the most critical moments, but less often than in FULL mode. There is a very small (though non-zero) chance that a power failure at just the wrong time could corrupt the database in journal_mode=DELETE on an older filesystem. WAL mode is safe from corruption with synchronous=NORMAL, and probably DELETE mode is safe too on modern filesystems. WAL mode is always consistent with synchronous=NORMAL, but WAL mode does lose durability. A transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash. Transactions are durable across application crashes regardless of the synchronous setting or journal mode. The synchronous=NORMAL setting provides the best balance between performance and safety for most applications running in WAL mode. You lose durability across power lose with synchronous NORMAL in WAL mode, but that is not important for most applications. Transactions are still atomic, consistent, and isolated, which are the most important characteristics in most use cases."
- EXTRA (3): "EXTRA is no different from FULL in WAL mode."
- OFF (0): "If the application running SQLite crashes, the data will be safe, but the database might become corrupted if the operating system crashes or the computer loses power before that data has been written to non-volatile storage."
- WAL-specific cost (wal.html §2.3): "Writers sync the WAL on every transaction commit if PRAGMA synchronous is set to FULL but omit this sync if PRAGMA synchronous is set to NORMAL." And: "Note that with PRAGMA synchronous set to NORMAL, the checkpoint is the only operation to issue an I/O barrier or sync operation ... If an application therefore runs checkpoint in a separate thread or process, the main thread or process that is doing database queries and updates will never block on a sync operation. ... The downside to this configuration is that transactions are no longer durable and might rollback following a power failure or hard reset."
- Hardware caveat (howtocorrupt.html §3.1): "Most consumer-grade mass storage devices lie about syncing." §3.2: "By setting PRAGMA synchronous=OFF, all sync operations are omitted."
- Other corruption vectors relevant to a local store (howtocorrupt.html): §1.3/1.4 deleting or mispairing hot journals / `-wal` files ("if the journal file does exist, it must be kept together with the database to avoid corruption"); §2.2 "The close() system call will cancel all POSIX advisory locks on the same file for all threads and all file descriptors in the process" (do not open the same DB file by other means in-process, e.g. an unrelated `File::open` + close of the DB path); §2.3 multiple SQLite copies linked into one binary (relevant when both rusqlite and sqlx would each bundle `libsqlite3-sys` — Cargo enforces one version); §2.4 mixed locking protocols; §2.5 unlinking/renaming while in use.
- Implication for Flowyard's commit boundaries (DESIGN.md §3): with `synchronous=FULL` in WAL, "Persist the attempt. Commit." is durable across power loss; with NORMAL it is durable only across process crashes, so a power loss could forget an admitted attempt whose external effect happened. FULL is the right default for a store whose rows authorize side effects.

## Retries, backoff, timeouts (busy handling with one writer)
- `SQLITE_BUSY` (rescode.html): "indicates that the database file could not be written (or in some cases read) because of concurrent activity by some other database connection, usually a database connection in a separate process. For example, if process A is in the middle of a large write transaction and at the same time process B attempts to start a new write transaction, process B will get back an SQLITE_BUSY result because SQLite only supports one writer at a time." `SQLITE_LOCKED` is the same-connection/shared-cache case.
- `SQLITE_BUSY_SNAPSHOT` (517): "occurs on WAL mode databases when a database connection tries to promote a read transaction into a write transaction but finds that another database connection has already written to the database and thus invalidated prior reads."
- Deferred vs immediate (lang_transaction.html): "DEFERRED means that the transaction does not actually start until the database is first accessed." A write statement in a deferred read transaction will "upgrade the transaction to a write transaction if possible, or return SQLITE_BUSY." "IMMEDIATE causes the database connection to start a new write immediately, without waiting for a write statement. The BEGIN IMMEDIATE might fail with SQLITE_BUSY if another write transaction is already active on another database connection." "EXCLUSIVE and IMMEDIATE are the same in WAL mode". rescode.html: "To avoid encountering SQLITE_BUSY errors in the middle of a transaction, the application can use BEGIN IMMEDIATE instead of just BEGIN to start a transaction."
- Busy handler limits (c3ref/busy_handler.html): "The presence of a busy handler does not guarantee that it will be invoked when there is lock contention. If SQLite determines that invoking the busy handler could result in a deadlock, it will go ahead and return SQLITE_BUSY to the application instead of invoking the busy handler." (the read-lock-promotion scenario). `sqlite3_busy_timeout`: "sets a busy handler that sleeps for a specified amount of time when a table is locked. The handler will sleep multiple times until at least "ms" milliseconds of sleeping have accumulated." One handler per connection; `PRAGMA busy_timeout` "sets the busy handler for the process, possibly overwriting any previously set busy handler."
- COMMIT can also be BUSY in rollback mode: "An attempt to execute COMMIT might also result in an SQLITE_BUSY return code if another thread or process has an open read connection." (lang_transaction.html; readers do not block WAL commits, but they block RESTART/TRUNCATE checkpoints.)
- With exactly one writer connection in the process, BUSY should only arise from: a second process (tooling) holding a write or a checkpoint, `SQLITE_BUSY_RECOVERY` ("another process is busy recovering a WAL mode database file following a crash"), or a reader connection in the same process being upgraded to write. Design rule: every write transaction is `BEGIN IMMEDIATE` on the single writer; readers never write; `busy_timeout` set anyway (a few seconds) for the tooling case.

## Flow control (recommended pragmas for a single-writer local workflow store)
Per connection unless noted:
```sql
PRAGMA journal_mode = WAL;          -- persistent in the file; set once at create/open
PRAGMA synchronous = FULL;          -- durable across power loss in WAL (default for the store)
PRAGMA busy_timeout = 5000;         -- covers checkpoints/tooling; not a substitute for BEGIN IMMEDIATE
PRAGMA foreign_keys = ON;           -- "the default setting for foreign key enforcement is OFF"; per connection
PRAGMA wal_autocheckpoint = 1000;   -- default; or 0 plus an explicit periodic PRAGMA wal_checkpoint(TRUNCATE) from the writer
PRAGMA journal_size_limit = 67108864; -- bound the -wal file left after checkpoints (value is a policy choice)
PRAGMA temp_store = MEMORY;         -- optional
PRAGMA application_id = <magic>;    -- "Applications that use SQLite as their application file-format should set the Application ID"
PRAGMA user_version = <schema version>; -- integer at offset 60; what rusqlite_migration uses
-- Optional, single-process only: PRAGMA locking_mode = EXCLUSIVE;  -- no -shm needed; blocks every other connection
-- On close (long-lived DB): PRAGMA optimize;
```
- Write path: one connection, `BEGIN IMMEDIATE`, short transactions, `COMMIT`; run `PRAGMA wal_checkpoint(PASSIVE)` opportunistically and `TRUNCATE` at quiet points from the same writer (checkpoint needs no live readers to reset the WAL).
- Read path: separate connection(s) for inspection/CLI with `query_only`; keep read transactions short so checkpoints are not starved.
- Do not: put the workspace on NFS/SMB; open the DB path with plain file APIs in-process (§2.2 close() lock cancellation); mix `synchronous=NORMAL` writes with "effect authorized" semantics; run two processes with different SQLite builds/locking VFS.
- `PRAGMA synchronous = NORMAL` is the documented "best balance" when power-loss durability is not needed; Flowyard can expose it as an explicit workspace option (e.g. for scratch/test workspaces) but not as the default.

## API ergonomics (rusqlite vs sqlx for a serialized single-writer design)

| Concern | rusqlite 0.40.2 | sqlx 0.9.0 (sqlite) |
|---|---|---|
| API style | sync, `Connection: Send + !Sync` | async facade; each connection on its own OS thread with a command channel |
| Write serialization | one connection on one thread by construction | needs a `max_connections(1)` writer pool or one held connection |
| `BEGIN IMMEDIATE` | `transaction_with_behavior(TransactionBehavior::Immediate)` | `Pool::begin_with("BEGIN IMMEDIATE")`; `begin()` is deferred |
| Default pragmas | none (you set them) | `foreign_keys` ON, `busy_timeout` 5 s, `synchronous` FULL, journal mode untouched |
| Migrations | `rusqlite_migration` (`user_version`), or hand-rolled | `sqlx::migrate!` + `_sqlx_migrations` table + `sqlx-cli` |
| Query checking | runtime | optional compile-time (`query!`, needs DB or offline data) |
| Hooks / backup / blob I/O | `hooks`, `backup`, `blob` features | update hooks not exposed (unverified); no backup API |
| Async story | `tokio-rusqlite` `.call(|conn| ..)` or `spawn_blocking` | native |
| SQLite linkage | `bundled` | `sqlite` (bundled) or `sqlite-unbundled`; `libsqlite3-sys` range |

rusqlite 0.40.2:
- Sync API; `Connection` is `Send` and `!Sync` (docs.rs auto-trait listing: `impl Send for Connection`, `impl !Sync for Connection`), so the natural pattern is one writer connection owned by one thread/actor. `Connection::transaction_with_behavior(TransactionBehavior::Immediate)` (docs: "IMMEDIATE cause the database connection to start a new write immediately, without waiting for a writes statement"), `busy_timeout`, `busy_handler`, `pragma_update`, `pragma_query_value`, `execute_batch`, `prepare_cached`, `backup`, `unchecked_transaction`. Features: `bundled` (statically compiled SQLite), `hooks` (commit/rollback/update hooks), `backup`, `blob`, `serde_json`, `chrono`/`time`/`jiff`, `trace`, `functions`, `vtab`, `load_extension`, `uuid`.
- Async story: run the connection on a dedicated thread. `tokio-rusqlite` 0.8.0: `Connection::open(..).await`, `conn.call(|conn| { ...rusqlite code...; Ok(v) }).await` (closure executed on the connection's thread); or `tokio::task::spawn_blocking` with an `Arc<Mutex<Connection>>`; or an mpsc actor. All of these serialize writes by construction.
- Migrations: `rusqlite_migration` 2.6.0 — "uses the `user_version` value instead" of a migrations table; `Migrations::new(vec![M::up("CREATE TABLE ...")]).to_latest(&mut conn)`; `const MIGRATIONS_SLICE: &[M<'_>]`; "forbid unsafe"; no external CLI.
- Pooling: none needed for the writer; `r2d2_sqlite` exists for read pools but is optional.

sqlx 0.9.0 (`sqlx-sqlite`):
- Each SQLite connection runs on its own OS thread: `connection/worker.rs` spawns `thread::Builder::new().name(params.thread_name.clone()).spawn(move || { let (command_tx, command_rx) = flume::bounded(params.command_channel_size); ... })` and the async API sends commands to it. Async ergonomics on top of a blocking core.
- `SqliteConnectOptions` defaults (docs/source): `foreign_keys` "SQLx chooses to enable this by default"; `busy_timeout` "The default busy timeout is 5 seconds."; `synchronous` "The default synchronous settings is FULL. However, if durability is not a concern, then NORMAL is normally all one needs in WAL mode."; `journal_mode` "SQLx does not set a journal mode by default, to avoid unintentionally changing a database into or out of WAL mode. The default journal mode for non-WAL databases is `DELETE` ... any commands in `sqlx-cli` which create a SQLite database will create it in WAL mode."; changing journal mode "requiring an exclusive lock ... You may get a `database is locked` (corresponding to `SQLITE_BUSY`) error if another connection is accessing the database file at the same time."; `locking_mode` default NORMAL; `statement_cache_capacity` 100; `serialized(false)` (FULLMUTEX only if true: "will also incur a significant performance penalty"); `create_if_missing` false by default; `optimize_on_close`.
- Transactions: `Pool::begin` ("Retrieves a connection and immediately begins a new transaction.") is a plain `BEGIN` (deferred); `Pool::begin_with(statement)` ("Retrieves a connection and immediately begins a new transaction using `statement`") lets you issue `BEGIN IMMEDIATE`. PR launchbadge/sqlx#4166 ("sqlx-sqlite: warning about write transaction deadlocks", closed unmerged 2026-02-18) documents the trap: with a pool, a deferred write transaction plus other tasks writing can stall until `busy_timeout`; the author concluded "splitting a single writer connection out from the read pool" was the better fix than a docs warning. The SQLite side of this is `SQLITE_BUSY_SNAPSHOT` above: the busy handler is not invoked for a snapshot upgrade, so `busy_timeout` cannot absorb it.
- Migrations: `sqlx::migrate!()` embeds `migrations/*.sql` and records them in `_sqlx_migrations` (table-based; underway's migration 0 shows `create table if not exists underway._sqlx_migrations (like public._sqlx_migrations including all)`); `sqlx-cli` manages them. Compile-time checked queries (`query!`) need a database at build time (`DATABASE_URL` or offline `.sqlx` data).
- libsqlite3-sys: "Only one version of `libsqlite3-sys` may appear in the dependency tree"; sqlx 0.9 uses a version range so it can coexist with rusqlite "If Cargo fails to select a compatible version, this means the other crate is using a `libsqlite3-sys` version outside of this range." spider's `disk` feature pulls sqlx 0.8 (see spider-rs note), which may constrain versions if both are in one binary.

Recommendation for Flowyard's serialized single writer:
- rusqlite on a dedicated writer thread (own actor or `tokio-rusqlite`), `TransactionBehavior::Immediate` for every write, `rusqlite_migration` with `user_version`, `hooks` feature for change notification if needed. Simpler, no pool, no deferred-transaction trap, no build-time DB. Read-only inspection connections opened separately.
- sqlx is justified only if async streaming of large result sets or compile-time query checking is wanted; then use two pools: a writer `SqlitePoolOptions::new().max_connections(1)` with `begin_with("BEGIN IMMEDIATE")` and a reader pool, and set `journal_mode(Wal)` explicitly since sqlx does not.

## Known limitations
- WAL: no network filesystems; `-wal`/`-shm` sidecar files; read-only access rules; page size frozen; checkpoint starvation under constant readers; large single transactions cannot be checkpointed until they commit (wal.html).
- `synchronous=NORMAL` in WAL loses the last transactions on power loss; `FULL` syncs on every commit (pragma.html, wal.html §2.3).
- Busy handler skipped when deadlock is possible; deferred-to-write upgrades return `SQLITE_BUSY_SNAPSHOT` without waiting (c3ref/busy_handler.html, rescode.html).
- Consumer storage may lie about fsync (howtocorrupt.html §3.1) — power-loss durability is conditional on hardware.
- sqlx: no default WAL; pool + deferred `BEGIN` contention (#4166); rusqlite: no async, `!Sync` connection.

## Relevance to Flowyard
- Borrow: WAL + `synchronous=FULL` default (matches DESIGN.md §3); `BEGIN IMMEDIATE` on a single writer connection as the only write path; `busy_timeout` for tooling; `foreign_keys=ON` per connection; `application_id` + `user_version` for workspace format/schema versioning (also what rusqlite_migration uses); `locking_mode=EXCLUSIVE` as an optional hard single-owner mode when no external inspection is needed; explicit `wal_checkpoint(TRUNCATE)` at idle points so the workspace directory does not accumulate a large `-wal`; the sqlite.org sentence "Transactions are durable across application crashes regardless of the synchronous setting or journal mode" as the precise claim to make in tests (subprocess kill != power loss, as DESIGN.md §7 already says).
- Avoid: pooled deferred transactions for writes; opening the workspace DB through any second library or plain file handle in-process; NFS/SMB workspaces; `synchronous=NORMAL` as a silent default; relying on `busy_timeout` to serialize writers.
- Answers to open questions:
  - Q5 (cooldowns persisted?): SQLite makes persisting per-host `next_allowed_at` rows cheap (one short IMMEDIATE transaction) — no reason to keep them in memory only.
  - Q7 (large outputs): inline BLOBs are fine for KB-scale; SQLite `blob` incremental I/O (rusqlite `blob` feature) exists, but Artifactum references keep the WAL small and checkpoints fast (large transactions delay checkpoints, wal.html).
  - Q2/Q3 (single owner, one-shot vs daemon): `locking_mode=EXCLUSIVE` or an OS file lock on a sidecar gives the single-owner guarantee; SQLite itself is indifferent to daemon vs one-shot, but "when the last database connection on a database file closes" a checkpoint runs automatically, so a one-shot process leaves a clean file behind.
  - Q9 (retry state): persisted `next_retry_at` costs one IMMEDIATE write; with FULL it survives power loss.
  - Q1, Q4, Q6, Q8, Q10: not addressed by SQLite.
