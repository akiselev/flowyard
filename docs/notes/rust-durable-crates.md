`durare` exists: a DBOS-compatible durable-execution SDK for Rust (crates.io 0.4.1, first published 2026-07-11, GitHub `SamuelXing/durare`), with Postgres, SQLite and in-memory `StateProvider`s and DBOS's `workflow_status` / `operation_outputs` schema. It is the only Rust crate found that does named-step checkpoint replay over SQLite; it is two months old, "community-maintained", 12 stars, 36 open issues (mostly DBOS parity items). `apalis` is the mature background-job framework (0.7.4 stable; 1.0.0-rc.10 rewrite with `apalis-sqlite`, `apalis-workflow`), a queue not a journal. `underway` (0.2.0, Postgres-only) does typed sequential step jobs and, on its unreleased main branch, activities with leases and per-call identity. `effectum` is a small SQLite job queue with checkpoints, dormant since 2024-07. `pgqrs` is a Postgres-native durable-execution engine with a SQLite mode. Nothing in the ecosystem provides Flowyard's combination (library, single owner, SQLite, keyed steps, structured map) out of the box; `durare` is the closest and also the clearest warning about replay-by-sequence-position.

## Crate: durare
- Process model: library in your worker; "There is no separate server: the engine is a library that lives in your worker and talks directly to the `StateProvider`." Multi-executor on Postgres (`FOR UPDATE SKIP LOCKED`, `LISTEN/NOTIFY`); SQLite "single-node deployments, local development ... full durability on a file database"; `InMemoryProvider` for tests.
- Execution model (README "How it works", verbatim): "Each side-effecting operation a workflow performs — a step, a sleep, a message receive, a child start — is recorded in the `operation_outputs` table, keyed by a deterministic per-execution counter and guarded by the operation's name. When a workflow is re-executed after a failure, operations that already ran return their recorded results instead of running again, and execution proceeds from the first checkpoint that is missing." "The consequence, as in every durable-execution system: workflow control flow must be deterministic. Wall-clock reads, random numbers, and anything else non-repeatable belong inside a step, where the result is recorded."
- Guarantees table (README): workflow state transitions/completion "exactly once"; step side effect "at least once — make external calls idempotent"; `#[transaction]` SQL "exactly once"; `recv` consumption "exactly once"; cron tick "once per tick across executors".
- Identity: `ctx.step(name, f)` calls `self.next_seq()` then `replay_or_guard(seq, name)`; `context.rs` doc: "a replay that finds a *different* operation recorded at this position fails with `Error::UnexpectedStep` — the workflow is non-deterministic, and the stored checkpoint would be the wrong step's result." Error text (`error.rs`): "workflow `{workflow_id}` step {step_id} is `{expected}` but `{recorded}` is recorded there — the workflow function is non-deterministic". Children: "unless `opts.workflow_id` is set, it gets the deterministic id `{parent_id}-{seq}`, and the parent→child link is checkpointed. On replay the same child is re-attached instead of being started again." Sleep: "The absolute wake time is fixed and persisted on the first call as an ordinary `DBOS.sleep` step in `operation_outputs`".
- Unreached recorded steps: `replay_or_guard` only checks the position currently executing; rows with a higher `function_id` are never read, so if new code finishes earlier they are silently orphaned (inference from `context.rs`; consistent with DBOS). No tooling flags them.
- Schema (`migrations/sqlite/1_initial_dbos_schema.sql`): `workflow_status(workflow_uuid TEXT PK, status, name, ..., executor_id, created_at, updated_at, application_version, application_id, recovery_attempts INTEGER DEFAULT 0, queue_name, workflow_timeout_ms, workflow_deadline_epoch_ms, inputs, started_at_epoch_ms, deduplication_id, priority)` with `UNIQUE (queue_name, deduplication_id)`; `operation_outputs(workflow_uuid, function_id INTEGER, function_name TEXT DEFAULT '', output, error, child_workflow_id, PRIMARY KEY (workflow_uuid, function_id))`; `notifications`, `workflow_events`, `streams`, `event_dispatch_kv`; later migrations add `workflow_schedules`, `queues`, `delay_until`, `was_forked_from`, serialization columns. Outputs are inline `TEXT` (serialized); no size limit or external reference mechanism. Comment in the SQLite migration: "Foreign keys require PRAGMA foreign_keys = ON, set on connect."
- Recovery: `DurableEngine::recover()` scans `PENDING`/`DELAYED` workflows for this `executor_id` (env `DBOS__VMID` overrides; default `"local"`). `engine.rs`: recovery on launch is "**off** — recovery is opt-in because it is only sound when each live process has a *unique* executor id (recovering "this executor's" pending work assumes the previous owner is gone, not running concurrently). Enable it for a single-process app". "Recovery re-dispatches beyond this count park the workflow in `MAX_RECOVERY_ATTEMPTS_EXCEEDED`" (`recovery_attempts` column). In-flight step at crash: re-run on replay (at-least-once), unless it was a `#[transaction]`.
- Retries: `StepOptions { name, max_retries: 0, backoff_factor: 2.0, base_interval: 100ms, max_interval: 5s, retry_if: None }` — retry loop is in-process inside `step_with`; the step's attempt count is not in the schema (issue #193 "[Parity] StepStatus (current_attempt / max_attempts) inside a step" is open), so a crash mid-retry restarts the count. Workflow-level `workflow_timeout_ms`/deadline persisted.
- Flow control: `WorkflowQueue` — "Per-process and global concurrency limits, rate limiting, priorities, delayed enqueue, deduplication (reject or return-existing), and partitioned queues." Keyed by queue name (DB-backed), not by host. `deduplication_id` gives "singleton per key" per queue.
- Fan-out: `ctx.start_workflow` children; `pipeline` example "queues: fan-out under a concurrency limit"; no map/collect; issue #154 "Durable wait-first combinator over workflow handles" open.
- Versioning: `application_version` recorded; "`recover()` resumes by application version, a version registry routes work across a fleet"; `ctx.patch(name)`: "A workflow that reaches this point for the first time ... records a marker and takes the new path. A workflow that already executed past this point before the patch existed takes the old path."; fork from an arbitrary step.
- Schedules: six-field cron `#[durare::workflow(schedule = "…")]`, schedule API "create, pause, resume, trigger, backfill"; durable `ctx.sleep`. Missed-run policy: backfill exists; default catch-up behaviour unverified.
- Cancellation: `Error::Cancelled` surfaced at the next step; cancelled workflows refuse replay; timeouts per workflow.
- Observability: admin HTTP server "with the standard DBOS endpoints", Conductor client, list/cancel/resume/fork; plain SQL (`SELECT workflow_uuid, function_id, function_name, output FROM dbos.operation_outputs;`).
- Maintenance: single maintainer, rapid releases, 36 open "[Parity]"/"[Bug]" issues (e.g. #173 "write_stream inside a step body consumes a workflow-level step id", #184 "Engine start path is missing deduplication validation the Client path has"). MSRV 1.88.

## Crate: apalis
- Versions: `apalis` 0.7.4 (stable, crates.io "updated 2026-09-15"), `apalis-sql` 0.7.4 (sqlite/postgres/mysql), `apalis-cron` 0.7.4; 1.0 line: `apalis` 1.0.0-rc.10 (2026-09-15), `apalis-core` 1.0.0-rc.10, `apalis-sqlite` 1.0.0-rc.9 (separate repo `apalis-dev/apalis-sqlite`), `apalis-postgres`, `apalis-redis`, `apalis-workflow` 0.1.0-rc.10, `apalis-board` (web UI). Repo `apalis-dev/apalis`: 1,381 stars, pushed 2026-09-15, 5 open issues. README: "Simple and extensible multithreaded background task and messages processing library for Rust"; "Task handlers are just async functions, with a macro-free API"; tower middleware (RetryLayer, TimeoutLayer, RateLimitLayer, ConcurrencyLimitLayer, CatchPanicLayer, tracing/sentry/prometheus).
- Process model: library; a `Worker` polls a backend; 0.7 uses `Monitor::new().register(WorkerBuilder::new("name").backend(storage).build_fn(f)).run()`; 1.0 uses `WorkerBuilder::new("email-worker").backend(storage).concurrency(2).parallelize(tokio::spawn).data(0usize).build(send_email).run()`.
- Execution model: job queue. A job is one function call; no step journal. `apalis-workflow` (1.0) adds `SteppedFlow::new("name").and_then(..).filter_map(..).delay_for(..)`; `apalis-sqlite` README: "Each stage only runs if the previous one succeeds; a failure at any step returns an error and the job can be retried from the beginning." (so step outputs are persisted between stages as new tasks, but a failing stage restarts the flow — unverified whether earlier stage results are reused).
- Schema (0.7.4 `migrations/sqlite/20220530084123_jobs_workers.sql`): `Workers (id TEXT NOT NULL UNIQUE, worker_type, storage_name, layers, last_seen INTEGER DEFAULT strftime('%s','now'))`; `Jobs (job TEXT NOT NULL, id TEXT NOT NULL UNIQUE, job_type TEXT, status TEXT DEFAULT 'Pending', attempts INTEGER DEFAULT 0, max_attempts INTEGER DEFAULT 25, run_at INTEGER, last_error TEXT, lock_at INTEGER, lock_by TEXT REFERENCES Workers(id), done_at INTEGER)`; `20250313213411_add_job_priority.sql` adds `priority`. Statuses: Pending, Running, Done, Failed, Killed, Retry. Payload inline as TEXT (JSON codec).
- Claiming and recovery (`sqlite.rs` 0.7.4): `UPDATE Jobs SET status = 'Running', lock_by = ?2, lock_at = ?3 WHERE id = ?1 AND job_type = ?4 AND status = 'Pending' AND lock_by IS NULL RETURNING *`; ack: `UPDATE Jobs SET status = ?4, attempts = ?5, done_at = strftime('%s','now'), last_error = ?3 WHERE id = ?1 AND lock_by = ?2`; heartbeat upsert into `Workers.last_seen`; orphan requeue: `UPDATE Jobs SET status = "Pending", lock_by = NULL, attempts = attempts + 1, last_error = "Job was abandoned" WHERE id IN (SELECT Jobs.id FROM Jobs INNER JOIN Workers WHERE status = "Running" AND workers.last_seen < ?1 LIMIT ?3)`. `Config`: `poll_interval`, `buffer_size`, `keep_alive`, `namespace`, `reenqueue_orphaned_after`. 1.0 `apalis-sqlite` README: "jobs are written to disk before processing begins, so a crash mid-flight won't silently drop work"; "workers emit periodic heartbeats; jobs held by a dead worker are automatically re-enqueued"; `TaskBuilder::new(x).run_after(d).priority(p).max_attempts(5)`; event-driven polling via SQLite update hooks (`connect_with_callback`).
- Retries: `attempts`/`max_attempts` in the row; backoff via `RetryLayer`/`reschedule()` (sets `run_at`); next-attempt time therefore persisted only when rescheduled, not for in-layer retries (unverified for 1.0).
- Identity: `TaskId` generated by the backend (ULID in 0.7 — unverified); no user-supplied idempotency key in the 0.7 schema (no unique constraint besides `id`).
- Schedules: `apalis-cron` runs a cron `Stream` in-process that produces jobs on tick; no persisted schedule cursor; missed ticks while down are not produced (inference from stream model; unverified).
- Maintenance: active, but mid-migration to 1.0 with a `-rc` series since 2025-12 and backend crates split into separate repos; docs.rs "latest" for `apalis` shows 0.7.4 while the README targets `1.0.0-rc.10`.

## Crate: underway
- Versions: 0.2.0 (2025-07-16) is the latest release; repo `maxcountryman/underway` (172 stars, pushed 2026-09-15, 17 open issues) is far ahead on main with an unreleased `Workflow`/`Activity` API and migrations dated 2025-12-28 to 2026-02-13. Postgres only ("Durable background workflows on Postgres"; "No extra broker or orchestration layer; queue coordination and task claiming happen in PostgreSQL").
- Execution model (0.2.0 docs): "Jobs are a series of sequential steps. Each step provides input to the next step in the series." "each step is treated as its own task, [and] steps are executed and then persisted, before the next task is enqueued." Steps return `To::next(value)`, `To::done()`, `To::delay_for(value, duration)`. State passed via context "is not serialized to the database and therefore not persisted between process restarts."
- main branch: `Workflow::builder().step(|cx, input| async { Transition::next(..) }).step(..).name("image-pipeline").pool(pool).build()`; `impl Activity for LookupEmail { const NAME: &'static str = "lookup-email"; type Input; type Output; async fn execute(..) -> underway::activity::Result<..> }` with `ActivityError::retryable("db_error", ..)`; `LookupEmail::call(&mut cx, &user_id)` (durable call with result) and `TrackSignupMetric::emit(..)` (fire-and-forget); "Transactional `*_using` APIs, retries, cron scheduling, heartbeats, and fencing".
- Schema (`migrations/20240921151751_0.sql`): `task_queue(name PK, dlq_name)`, `task_schedule(name, schedule, timezone, input jsonb)`, enum `task_state (pending, in_progress, succeeded, cancelled, failed)` (+ `waiting` in migration 6), `task(id uuid, task_queue_name, input jsonb, state, retry_count, max_attempts 5, initial_interval_ms 1000, max_interval_ms 60000, backoff_coefficient 2.0, error_message, timeout interval '15 minutes', ttl '14 days', delay, concurrency_key text, priority, created_at, updated_at, started_at, succeeded_at, last_failed_at)`; `create unique index idx_task_concurrency_key_unique on underway.task (task_queue_name, concurrency_key) where concurrency_key is not null and state in ('pending', 'in_progress');` — a persisted singleton-per-key rule. Migration `20251228120000_0.sql` makes `retry_policy` a composite `(max_attempts, initial_interval_ms, max_interval_ms, backoff_coefficient, jitter_factor)` defaulting to `row(5, 1000, 60000, 2.0, 0.5)`. Migration 6 adds `activity_call(id, task_queue_name, workflow_run_id, step_index, call_key, activity, input, output, error, state, attempt_count, available_at, ..., unique (task_queue_name, workflow_run_id, step_index, call_key))` with `pg_notify` on pending; migration 7 `activity_call_attempt(activity_call_id, attempt_number, state, error, started_at, completed_at)`; migration 9 adds `task.run_at, attempt_count, current_attempt, lease_expires_at`, `activity_call.timeout_ms 900000, max_attempts 5, lease_expires_at`, indexes `idx_task_claim_pending` (pending by priority/run_at) and `idx_task_claim_stale` (in_progress by `lease_expires_at`).
- Identity (main): activity call = `(workflow_run_id, step_index, call_key)`; step = index in the builder. Mismatch/unreached: not documented; the unique key means a re-run step with the same `call_key` re-attaches to the recorded call (inference from schema).
- Crash recovery (main): leases with heartbeat; stale `in_progress` tasks/activity calls become claimable when `lease_expires_at` passes (schema + "heartbeats, and fencing"). 0.2.0: `timeout` (15 min default) bounds a task; no lease column in 0.2.0's initial schema.
- Retries: persisted per task (`retry_count`, policy columns, `last_failed_at`); backoff computed from policy with jitter 0.5; per-activity `max_attempts` and attempt rows on main. Failure classification: `ActivityError::retryable(..)` vs non-retryable (main).
- Schedules: `task_schedule` with zoned cron `"0 2 * * *[UTC]"` / `"@daily[America/Los_Angeles]"`; `enqueue_using(&mut *tx, ..)`/`schedule_using(..)` inside the caller's transaction. Missed-run policy unverified.
- Maintenance: single maintainer; released API (0.2.0) and main diverge substantially; Postgres-only rules it out as a Flowyard backend but its schema is the best Rust precedent for attempt/lease/call-key modelling.

## Crate: effectum
- 0.7.0 (2024-07-23), repo `dimfeld/effectum` pushed 2024-07-23, 48 stars, 2 open issues — dormant. "A Rust job queue library, based on SQLite so it doesn't depend on any other services." Embedded via `rusqlite`; `Queue::new(&PathBuf::from("effectum.db"))`; `JobRunner::builder("remind_me", f)`; `Worker::builder(&queue, context).max_concurrency(10).jobs([..])`; `Job::builder("remind_me").run_at(..).json_payload(..).add_to(&queue)`.
- Schema (`migrations/00001-init.sql`): `active_jobs(job_id PK, active_worker_id, priority, run_at, started_at, expires_at)` with partial indexes for ready (`active_worker_id is null`) and running (`expires_at`); `jobs(job_id PK, external_id blob UNIQUE, job_type, priority, weight, status, from_recurring_job, orig_run_at, payload blob, checkpointed_payload blob, current_try, max_retries, backoff_multiplier, backoff_randomization, backoff_initial_interval, added_at, default_timeout, heartbeat_increment, started_at, finished_at, run_info)`; `recurring(external_id UNIQUE, base_job_id, schedule)`.
- Recovery: `JobRecoveryBehavior` — "How to treat jobs which are already marked as running when the queue starts. This accounts for cases where the process is restarted unexpectedly." Variants: `FailAndRetryImmediately` ("Mark the job as failed, and schedule the next try to run immediately. (Normal worker concurrency limits will still apply.)"), `FailAndRetryWithBackoff`. `job_recovery.rs` records `RunInfo { success: false, ..., info: "Job failed due to unexpected process restart" }` and completes the job as failed when `current_try + 1 > max_retries`. Mid-job progress: `RunningJob::checkpoint_json/checkpoint_payload` stores `checkpointed_payload` so a retry resumes from user-defined progress; heartbeats extend `expires_at`.
- Retries: `Retries { max_retries, backoff_multiplier, backoff_randomization, backoff_initial_interval }` persisted per job; next `run_at` persisted on retry. Recurring jobs via cron schedule string.
- Identity: `external_id` unique (user-suppliable), `job_type` string.

## Other crates (brief)

## Step and operation identity (comparative)
- durare: sequence counter + name guard (`UnexpectedStep` on mismatch; silent orphaning of later rows).
- underway main: `(workflow_run_id, step_index, call_key)` unique — the only crate with a user-supplied per-call key.
- pgqrs: user-supplied step name per `workflow_step` call (collision behaviour unverified).
- apalis, effectum: job id only; `effectum.external_id` and `underway.concurrency_key` are the dedup keys.

## Crash recovery of in-flight work (comparative)
- Journal crates (durare, pgqrs): the step re-runs on replay; at-least-once unless the step is a DB transaction (`#[durare::transaction]`).
- Queue crates: lease/heartbeat + orphan requeue (apalis `Workers.last_seen` + `reenqueue_orphaned_after`; underway `lease_expires_at`; effectum `expires_at` + `JobRecoveryBehavior` at startup). effectum is the only one with a single-process "on startup, everything marked running is dead" rule — the same assumption Flowyard's exclusive owner makes.
- User-declared recovery policy: only effectum (`JobRecoveryBehavior` at queue level) and durare's `retry_if`/transaction distinction; none has per-operation "repeat-safe / idempotent effect / uncertain" classes.

## Retries, backoff, timeouts (comparative)
- Persisted attempt count + next time + policy: underway (`retry_count`, policy columns, jitter 0.5), effectum (`current_try`, backoff fields, `run_at`), apalis (`attempts`, `max_attempts`, `run_at` on reschedule).
- In-memory only: durare step retries (`StepOptions`), spider-style loops.
- Timeouts persisted: underway (`timeout` interval, activity `timeout_ms`), durare (`workflow_timeout_ms`), effectum (`default_timeout`, `heartbeat_increment`).

## Flow control, fan-out, versioning, schedules (comparative)
- Concurrency: apalis worker `concurrency(n)` + tower layers (in-memory); durare queues (DB-backed limits, rate limits, priorities, partitions); underway `concurrency_key` unique index (persisted singleton) and worker `concurrency_limit`; effectum worker `max_concurrency`, job `weight`. No crate keys limits by host.
- Fan-out: durare child workflows with deterministic ids; apalis-workflow `SteppedFlow` combinators (sequential/dag); underway sequential steps and activity `emit`; nothing records a fixed work set with per-item outcomes.
- Versioning: durare `application_version` + `patch` + fork; others none.
- Schedules: durare cron + schedule API + backfill; underway `task_schedule` zoned cron in-DB; effectum `recurring` table; apalis-cron in-memory stream. Missed-run policies undocumented everywhere except durare's backfill command.

## API ergonomics
durare quick start, verbatim (README):
```rust
use std::time::Duration;
use durare::{DurableContext, DurableEngine, Result, WorkflowOptions};

#[durare::step]
async fn charge_card(ctx: &DurableContext, order_id: String) -> Result<String> {
    // Any side effect: an HTTP call, an email, a write to another system.
    // It runs once; the result is checkpointed and replayed thereafter.
    Ok(format!("ch_{order_id}"))
}

#[durare::workflow]
async fn process_order(ctx: DurableContext, order_id: String) -> Result<String> {
    let charge_id = charge_card(&ctx, order_id).await?;
    ctx.sleep(Duration::from_secs(24 * 3600)).await?; // durable timer
    Ok(charge_id)
}

#[tokio::main]
async fn main() -> Result<()> {
    let engine = DurableEngine::connect("postgres://localhost/app").await?.build().await?;
    engine.recover().await?; // resume whatever a previous process left unfinished

    let handle = engine
        .start_with(ProcessOrder, "1001".into(), WorkflowOptions::with_id("order-1001"))
        .await?;
    println!("charged: {}", handle.await?);
    Ok(())
}
```
- Delightful (durare): `#[step]` on an ordinary `async fn` generates a typed marker (`ProcessOrder`) and registration; `ctx.sleep` is durable; `WorkflowOptions::with_id` gives explicit run identity; in-memory provider for tests; SQL-inspectable state. (apalis): handler = async fn with extractors (`Data<T>`, `TaskId`, `Attempt`), tower layers. (underway main): compile-time-checked step chains and `Activity` trait with `NAME`. (effectum): `checkpoint_json` mid-job.
- Painful / footguns: durare's `&DurableContext` is `Clone`-able/shared, so two steps awaited concurrently (`join!`) race for the same sequence number (DESIGN.md §2 concern; durare has no `&mut` guard); silent orphaning of unreached rows; step retries not persisted; recovery opt-in and executor-id semantics; docs/README examples target `durare = "0.3"` while 0.4.1 is current. apalis: 1.0-rc churn, backends split into repos, docs.rs vs README version mismatch, job payload retry-from-beginning in `SteppedFlow`. underway: Postgres only, unreleased main. effectum: dormant.
- Scraping pipeline in these crates: durare could express `refresh_source` as a workflow with `acquire`/`extract` steps and a child workflow per event, but per-host cooldowns, artifact references and a keyed `map` are all user plumbing, and every fetch inside a step is at-least-once; apalis/underway would model each fetch as a job with `concurrency_key` (underway) — coordination back into a snapshot is again user code.

## Known limitations
- durare: open parity/bug issues (#173, #184, #193, #154 among 36); recovery off by default and unsound without unique executor ids (engine.rs); "community-maintained" single author; no SQLite-specific pragmas documented (unverified what `SqliteProvider` sets).
- apalis: 1.0 still rc (`1.0.0-rc.10`), storage crates rc; 0.7 schema has no idempotency key; cron not persisted.
- underway: Postgres only; released 0.2.0 lacks leases/activities that main has.
- effectum: no release since 2024-07; single-process assumption implicit.
- pgqrs: SQLite mode positioned for "testing and embedded"; 829 downloads.

## Relevance to Flowyard
- Borrow: DBOS/durare's two-table core (`workflow_status` + `operation_outputs` keyed by run + position + name) as the minimum journal, but replace the counter with Flowyard's explicit operation keys; durare's `UnexpectedStep` error wording as the template for Flowyard's mismatch error; durare's guarantee table (state transitions exactly-once, side effects at-least-once, transactional steps exactly-once) as the honest contract to publish; underway's `activity_call` unique key `(run, step_index, call_key)` and its `attempt` table + `lease_expires_at` as the shape for Flowyard's attempts (minus leases); underway's partial unique index on `(queue, concurrency_key) where state in (pending, in_progress)` as the persisted singleton-per-key rule; effectum's `JobRecoveryBehavior` and "Job failed due to unexpected process restart" `RunInfo` as the single-owner startup recovery step; underway's retry policy row with `jitter_factor` and effectum's persisted `run_at` as the model for persisted next-retry times; pgqrs's `CANCELLING`/`CANCELLED` two-phase cancel.
- Avoid: sequence-position identity with silent orphans; a shared `Clone` context that permits concurrent step calls; recovery that depends on executor-id uniqueness conventions; in-memory step retries; queue-only models where a "workflow" is a job that restarts from the beginning (apalis `SteppedFlow`); Postgres-only designs; adopting an rc-stage framework as the core dependency.
- Answers to open questions:
  - Q1: durare/DBOS ignore recorded operations past the new code's end (inference from `replay_or_guard`); underway/apalis n/a (no replay).
  - Q2: underway `concurrency_key` partial unique index (persisted, per queue); durare `deduplication_id` unique per queue; effectum `external_id` unique; apalis 0.7 none.
  - Q3: all are library workers polling a store; durare and effectum run inside the app process; underway/apalis expect long-lived workers; none is one-shot-and-exit by design, though all can be driven that way.
  - Q4: dispatched via persisted queue and worker pool in apalis/underway/effectum/pgqrs; durare executes the workflow future in the engine that claimed it, steps inline in that future (`ctx.step` awaits the closure), with queues only at workflow granularity.
  - Q5: none keys limits by host; durare queue rate limits are DB-backed per queue; apalis `RateLimitLayer` in-memory.
  - Q6: durare docs say only that non-repeatable reads belong in steps; no cost guidance.
  - Q7: all inline serialized `TEXT`/`jsonb`/`blob` outputs; no reference mechanism or size limit documented.
  - Q8: durare `application_version` routing + `patch` (warn-and-branch); others none.
  - Q9: underway/effectum/apalis persist attempt count and next time (jitter in underway policy); durare persists only workflow-level `recovery_attempts`.
  - Q10: undocumented except durare `backfill`; apalis-cron/effectum recurring inferred to skip missed ticks (unverified).
